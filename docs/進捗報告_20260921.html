公共交通オープンデータチャレンジ2026 応募作品／transit-accessibility 拡張

2026-09-21 ／ ブランチ fix/network-and-isochrone（12コミット、push済） ／ 対象: 室蘭市・道南バス GTFS-JP

1. 要約

本期間の作業は大きく3つ。(1) 計算基盤の重大なバグ修正、(2) 核心機能「時間空白診断」の実装、(3) 処方（改善施策）モジュールの新設。 とくに(1)では、発表・面接で使う予定だった数値が壊れたネットワーク上のものであることが判明し、全て再計算した。

最も重要な変更: ネットワーク構築が所要0分の区間を捨てており、148停留所（すずらん団地・みどり団地など）がモデル上バスで永久に到達不能になっていた。修正により到達停留所数が時間帯により2〜8倍変化し、主要な分析結果がすべて変わった。

2. 修正した計算バグ

2.1 ネットワーク構築の区間欠落（最重要）

build_network.py が travel_time > 0 の区間しか採用していなかった。GTFS-JPの時刻は分単位のため、近接停留所間は所要0分になる。

項目値
平日ダイヤの全区間115,415
所要0分として除外されていた区間9,760（8.46%）
影響を受けた便1,833 / 2,837便
モデル上バスで到達不能だった停留所148箇所 → 0箇所

時刻表の時刻は絶対値なので、0秒エッジを残しても誤差は停留所あたり1分未満で、便の総所要時間には累積しない。時刻逆転（負値）は0件だった。

2.2 バス停削除シミュレーションの同種バグ

同じ欠陥が削除ロジック内部にも残っていた。何も削除しなくても到達圏が 212 → 91 に壊れる状態で、削除の影響を大きく過大評価していた。修正後、東室蘭駅東口の削除による到達不能は 132箇所 → 2箇所（当該停留所のみ）となり、「主要ハブ削除で24箇所が孤立」という従来の知見は成立しなくなった。

2.3 逆方向到達圏（集客圏）の徒歩連続

順方向にある「徒歩の連続禁止」が逆方向に無く、300m徒歩エッジを無制限に連鎖できていた。集客圏が18.2%過大（280→229停留所）。両者で移動ルールが異なると前後比較が成立しないため修正。

3. 更新した分析結果

修正後ネットワーク・平日ダイヤ・室蘭駅前起点・制限60分での実測値。

知見従来（誤）修正後
時間帯格差13.2倍27.6倍（5時台11 / 10時台304）
路線廃止の非対称性42路線中5102路線中5

差別化の主張が強化された。設計更新メモの「同じ地点でも時間帯で到達可能性が13倍変わる」は 27.6倍 に更新できる。一方、減便の非線形性とハブの重要性は従来ほど鮮やかな結果ではなくなった。

4. 新機能

4.1 時間空白診断（核心）

空白人口の定義を「1つのバス停からの到達圏」から「各メッシュから生活拠点に制限時間内に着けるか」へ変更。この向きなら拠点1つ・時間帯1つあたり逆方向ダイクストラ1回で全メッシュの判定が出るため、全メッシュを起点にする必要がない。3,079メッシュ×17時間帯の集計が0.10秒。

メッシュ重心→最寄りバス停（500m以内）の徒歩区間を新設。従来はバス停間300mの徒歩エッジのみで「そもそもバス停まで歩けるか」が評価されていなかった。徒歩圏にバス停が無いメッシュは静的空白として、時刻表由来の時間空白と区別する。

4.2 土日祝ダイヤ対応

calendar.txt の monday==1 のみを見ており平日しか扱えなかった。交通空白は休日にこそ深刻なのに測れていなかった。平日806便／土曜674便／日祝670便。

4.3 3Dカラム可視化

500mメッシュごとに柱を立て、高さ＝空白人口、色＝18時間帯のうち何時間帯で空白になるか。到着時刻スライダーで柱が伸縮する。Streamlit 無しで開ける単体HTML版を docs/ に同梱。

設計メモは250mメッシュを想定していたが、100mメッシュは1kmの10等分のため250mには整数で割り切れない。標準メッシュ体系で作れる500m（5×5セル）を採用した。

5. 休日の朝という発見

ダイヤ別に空白人口を測ったところ、曜日という新しい軸が現れた。拠点＝東室蘭駅東口、60分以内。

到着時刻平日土日祝
7時着21,19538,322（市の46.1%）
9時着19,86713,825
12時着20,48820,326
17時着24,24526,417

休日の朝は市の46%が拠点に着けない。一方、日中はむしろ休日のほうが良い。平日と土日は互いに素な時刻表なので、どちらが広いかは時間帯で入れ替わる。

当初の仮説は誤りだった。「休日は常に空白が多い」と想定してテストを書いたが、9時台では逆転していた。決め打ちの大小比較を捨て、代わりに「便を増やせば到達範囲は広がる」という単調性（土曜+平日 ⊇ 各々）をテストに据えた。

6. 処方（改善施策）モジュール

診断に対し「何をすれば埋まるか」を同じ指標で答える。核心が時間空白なので、処方も時間軸のもの（増便・ダイヤシフト）を中心に置いた。

補足: 「代替路線をどこに引くか」「停留所をどこに新設するか」は空間軸の処方で、2025年優秀賞「コミバスをつくろう！」と正面から競合する。診断で時間空白を示しながら処方が空間軸では、主張の軸がずれる。

6.1 基盤の refactor

従来 simulate_* は改変エッジを内部で作った直後に前方ダイクストラを回し、起点1停留所からの到達圏しか返さなかった。空白人口は逆方向到達圏で計算するため、施策の効果を核心指標で測れなかった。改変後エッジを返す関数に分離し、engine.scenario() で一時適用できるようにした。

6.2 結果（休日7時着・基準38,322人）

施策7時の削減全日の削減追加便運行キロ増
増便 選んだ3路線すべて010,59512247.6
増便 10絵鞆・工大線08,847120.3
シフト 八丁平すずかけ線8,2144,77300.0
シフト 絵鞆循環線0−1,719（悪化）00.0

6.3 分かった3つのこと

  • 便数で対象路線を選ぶと完全に外れる。最多便の鉄北北口線は129停留所を通るが空白地域は0箇所で、増便しても1人も減らない。効くのは便数の少ないローカル線。空白地域の停留所数で候補を自動順位づけする機能を追加した。
  • 最も効率的なのは1便追加。10絵鞆・工大線は休日に1便しか走っておらず、1便足すだけで全日の延べ空白が8,847人減る（20.3km）。ただしこれは当該路線の特殊事情で、一般化はできない。
  • 全日で評価しないと危険。当初7時着のみで評価し、ダイヤシフトが「費用ゼロで8,214人改善」と出た。全日で見ると13時・15時が悪化して実質4,773人減。絵鞆循環線のシフトに至っては7時の改善がゼロで全日1,719人の純悪化なのに、単一時刻では「効果0」と無害に見えていた。評価を全18時間帯に変更した。

費用は実額が不明なため「運行キロ＝便数×路線長」を代理値とした。バス事業のコストは慣例的に円/実車走行キロで表され補助金算定も走行キロ基準のため、後から単価を掛ければ金額になる。路線長は停留所間の直線距離の和で、実道路距離より短めに出る（shapes.txt は未使用）。

8. 品質

テスト 975件すべて合格（内訳: 473 / 137 / 286 / 24 / 13 / 17 / 25）。新規に test_blank_area、test_day_type、test_scenario、test_prescription を追加。

  • edges_after_* と simulate_* の結果一致を検証しており、片方だけ直してずれる事故を検出できる。
  • 既知の失敗だった「全路線同時廃止」テストは、高速バスを除外した路線一覧だけを廃止していたテスト側の不具合だったため修正。

9. 限界と残作業

  • 勾配（DEM）は未着手。徒歩速度を一律に落として効果の上限を測ったところ、半減（Tobler式で S=+0.20 相当）でも空白人口は+9.1%にとどまった。全メッシュが急勾配という前提での上限値なので実際はより小さい。DEM取得の工数に見合うかは要判断。
  • 実画面の目視確認が不十分。3Dマップは単体HTML版のみブラウザで確認済み。処方モードは AppTest（要素とデータ）までの検証で、実画面は未確認。
  • calendar_dates.txt（特定日の運休・追加）は未対応。祝日ダイヤは「日祝」の service_id で近似している。
  • 徒歩エッジ生成が停留所2,329件の総当たり（542万回）で、大規模都市では実用にならない。
  • main へのマージは未実施。公開中のアプリには未反映。
  • デマンド交通（GTFS-Flex）は機能過多を避けるため削除した。コンテストの2026年重点項目ではあるため、復活させる場合は git 履歴から戻せる。
